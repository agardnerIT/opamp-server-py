# Decisions

## Design Principles

- As simple as possible. As complex as necessary.

## Commit/Issue Protocol

- When a task is done, write a summary to the Git issue then close it out.
- Never write sensitive information to Github issues
- Link issues to commits (use "Closes #XX" or "Refs #XX" in commit message)
- NEVER close issues until the user confirms they're resolved
- Always add a comment to issues and comments that this work was assisted by AI
- Compact your memory after we close each issue

## Issue Handling

- When asked to do an issue, FIRST look it up and understand it
- Create as mant subtasks as you need to simplify work
- Fix the issue and add/update comments on the issue
- Link commits to the issue but DO NOT close until explicitly told
- This applies to all future issue work

## Scope Changes

- If scope changes (because user wasn't clear enough in issue), update the original issue/comment to explain the new scope and why you're doing more work

## Environment Variables

- All new configurable settings should be added to `.env.sample`

## Planning Process

- When planning an issue, post the plan to the GitHub issue BEFORE modifying any code
- Wait for human review/approval before actioning
- You can always create subtasks if a task is too big / if it's easier

## Issue Closing

- ALWAYS push commits after closing so the fix shows in the issue
- User must be able to see which commit/PR closed the issue

## Additional Ideas

- ALWAYS ask for clarification if needed
- ALWAYS prompt user with ideas they may not have thought of

## Config Push (epic #93)

- Work starts in new sessions. Read epic #93 first: threat model, design decisions D1-D9, and the dependency graph are all there. Do not relitigate a decision without saying why in the issue.
- **Nothing ships before the security prerequisites** (#94 agent auth, #95 admin auth, #96 fail-closed posture). Config push on today's server = fleet takeover.
- Two-phase flow is mandatory: **propose → approve → apply**, with `approver` as a separate role from `operator` (that is what makes approval meaningful).
- **MCP may only propose/validate.** Apply/approve/rollback are never exposed to MCP, and write tools are absent (not failing) unless `OPAMP_MCP_ALLOW_WRITES=true`.
- Never auto-retry a `FAILED` or auto-reverted config: poison the revision, require re-approval.
- A **redacted** config body must be un-pushable. Pushing one silently wipes credentials fleet-wide.
- Agent-side reality (verified against upstream): remote config is applied by the **OpAMP Supervisor**, not by `extension/opampextension` (it never advertises `AcceptsRemoteConfig`). The supervisor persists `last_recv_remote_config.dat` + `last_working_remote_config.dat` and auto-reverts on failure, which is why naive hash reconciliation loops.

## Commits

- NEVER commit to git until user confirms issue is resolved
- NEVER push without explicit user approval

## UI Changes

- Whenever there are UI changes, take screenshots and add them to the README so users always see the latest and greatest UI
- Before taking screenshots: start a collector (`~/tools/otelcol-contrib --config=collector/config.yaml`). Wait 5 seconds then start the UI. Disregard the initial collector error logs. That's expected as the collector cannot connect.

## Dependencies

- Always keep dependencies up to date with latest versions
- Check for updates regularly and update requirements files accordingly

# Technical Discoveries

- **Audit log (#97)** is `server/state.py::SQLiteAuditStore` (hash-chained) + `server/audit.py` (the only write path). `audit_event()` = best-effort, never raises, log line first (denials/observability); `audit_required()` = fail-closed, raises `AuditError` (privileged mutations). **Ordering contract: pre-write then act** — a successful action is exactly one row; a post-record mutation failure appends a second row with `result="error"`. Do not "simplify" this into post-write auditing: that is what makes "fail closed" aspirational.
- Chain: `entry_hash = sha256(canonical JSON of ts/actor/actor_kind/role/action/target_kind/target_id/revision_id/config_hash/result/detail_json/prev_hash)`, `id` deliberately excluded (assigned by SQLite, unverifiable otherwise), genesis = 64 zeros. `append()` uses `BEGIN IMMEDIATE` around read-tail-then-insert, else two workers fork the chain. Existing #94/#95 call sites are mapped, not rewritten: `principal`→actor, `result`→result, rest→redacted `detail_json`; `agent_auth.*` events become `actor="agent:<id>"`, and an unauthenticated agent failure is `anonymous`/`actor_kind="agent"` with `claimed` in detail.
- Retention: `AUDIT_RETENTION_DAYS` (default 365, `0`=forever) pruned from `periodic_cleanup` at most hourly; `prune()` appends an `audit.checkpoint` row recording `pruned_through_hash` **before** deleting, and `verify()` accepts a non-genesis first `prev_hash` only when a checkpoint records it. Deleting rows before the checkpoint still reads as tampering. A second prune never eats the checkpoint (checkpoints are excluded from the delete query).
- Breaker: 5 consecutive best-effort insert failures → 60s pause (`available()` false, `posture.audit_enabled()` false → `/health` `audit:false`); `audit_required()` ignores the breaker on purpose.
- `OPAMP_AUDIT_ENABLED` now defaults **true** and `audit` is the **fourth** config-push posture requirement (`posture.requirements()`), so `unmet_requirements()` can name it and push is refused without it. Tests that asserted three requirements / `audit:false` were updated.
- `audit` reached feature parity in all four layers: `opamp_client.audit_log/audit_verify/audit_export`, `opampctl audit list|verify|export` (+ **offline `--db`** paths), MCP `audit_log`/`audit_verify`/`audit_export` (read-only, never write-gated), skill doc. Export rendering lives once in `audit.format_entries()` with `AUDIT_EXPORT_COLUMNS` — api/cli/offline must not grow a second implementation.
- `opamp_client` bug found while wiring exports: `_request()` sniffs `.json()` first, and a one-row JSONL export *is* valid JSON → returned a dict. Exports use `_request_text()` (raw body) now; `_send()` holds the transport/error mapping for both.
- `tests/test_audit.py::AUDITED_ROUTES` + `EXPLAINED_ROUTES` is the #97 "no write route forgets" inventory: adding a mutating route fails the test until it is either audited or explained. New mutating routes must land in one of those maps.
- Basic-auth success is **not** audited per request (one row per request is the flood risk); `POST /auth/session` logins are, and failed Basic attempts only show in `opamp_admin_auth_failures_total` until the lockout fires (which is audited).

- **Push delivery (#102)** is `server.ws.send_to_agent()` (async) + `send_to_agent_threadsafe()` (routes are sync `def` → threadpool, and `asyncio.Queue.put_nowait` is **not** thread-safe; the wrapper is `run_coroutine_threadsafe(...).result(CONFIG_PUSH_WAIT_SECONDS)`). `remote_config` owns the single decision (`decision_for()`), and there are exactly two builders over it: `offer_for()` (reply path, records at build time) and `push_frame()` (unsolicited, returns a **framed** `ServerToAgent` — forgetting `encode_message` puts an unframed protobuf on the wire and every client fails with "unsupported header value"). Strip the framing and the first protobuf byte (0x0a) becomes the varint header.
- **Delivery is recorded on write, not on queue** (`on_sent` callback in `_writer`, after `send_bytes`). That is what makes a bounded send queue safe: a dropped or superseded frame consumes no attempt, so the next report re-offers it. `offer_for()` keeps recording at build time on purpose — the offer is in the same response body.
- **`ConnectionRegistry` keeps `Dict[bytes, int]` plus a `Connection` handle** (queue, loop, principal, token bucket, `config_slots`, `closed`). Reads (`handle_for(uid)`) are single-key lookups returning the handle; multi-key mutations take a `threading.Lock` (a `threading` lock, because push routes call in from threadpool threads). `serve()` opens before the receive loop and `close()`s + drains in the `finally`, so `opamp_ws_config_pending` cannot leak.
- **Config frames never overtake:** a new push for a uid marks the queued older frame `superseded`; the writer skips it and never calls `on_sent`. Replies are never superseded, and drop-oldest eviction prefers… whatever is oldest, which is why a *reply* is safe (it is always the newest frame) and a dropped config is just re-delivered.
- **Throttling is drop-not-block**: per-connection token bucket (`CONFIG_PUSH_RATE_PER_SECOND`/`CONFIG_PUSH_BURST`) + `CONFIG_PUSH_MAX_CONCURRENT` global in-flight cap. A throttled push is `queued`, never an error. Heartbeats are replies, so they are never throttled or superseded.
- **`delivery.state` vocabulary is derived, never stored**: push responses say `delivered`/`queued`/`unchanged` (+ `reason`); `assignment.state` says `none|queued|delivered|applied|failed|poisoned|unconfirmed`. `applied` requires the agent's reported hash to equal ours — `AgentState.last_remote_config_hash` is stored **hex** while the wire/`MessageToDict` form is **base64**, so `reported_status()` converts and `reported_hash()` accepts either (getting this backwards makes every agent look like it never applied anything, and makes deliver-now re-push forever).
- **`POST /agent/{id}/config/deliver` needs `operator`, not `approver`**: it re-sends the already-active revision and moves no pointer (D5), so there is nothing to approve. It is audited `config.deliver` **pre-write**; a refusal on principal grounds appends the documented second row with `result="error"` (the actor is passed down through `deliver_now(principal=…)` because the transport does not know who asked).
- `delivery_channel` (`push` | `reply`) is one nullable `desired_configs` column, reset by `_assign_on` like the other delivery facts. `reply` covers both transports (an HTTP poll or a WS message/reply) — it means "carried on the agent's own request", which is the honest distinction from a push.
- MCP has **no** deliver tool at any setting (D9): a client that can deliver makes its own proposal arrive on its own schedule.
- Bench after #102: 538 msg/s / p50 2.1 ms vs 541 / 2.1 ms before (200 agents, 4 clients) — the per-message `Outbound` wrapper costs nothing measurable.

- **Capacity baseline (#109, measured)**: ~450 OpAMP msg/s per uvicorn worker (p50 2.0 ms), because `_apply_status_report` calls `AGENT_REGISTRY.update()` ~5 times per message and each call rewrites the **whole** row (INSERT OR REPLACE + JSON re-serialisation of description/effective_config/components). 94% of message time is that write. Multi-worker does **not** help (+11%, worse p99) — writes serialise on the SQLite write lock **and** `AGENT_REGISTRY` is a per-process dict, so `GET /agents`/stale cleanup diverge per worker. Documented topology: one worker until #109 is fixed. RAM ~38 KB/agent, row ~10 KB JSON. `PRAGMA synchronous=NORMAL` does *not* help here (0.35→0.34 ms) — do not weaken durability for it.

- Admin auth (#95) is `server/auth.py`: `Principal` (name, role, method, session_hash), role ladder `viewer < operator < approver < admin` (`ROLE_LEVELS`, `role_satisfies`), `require_roles(request, role)` / `require_role(role)` dependency, and `require_admin()` kept as an alias for `role_satisfies(..., "admin")` so old call sites and Streamlit pages still work.
- **Read-only mode is read-open / write-closed**: with no credential configured, `require_roles(viewer)` returns an anonymous `Principal` and every higher role gets 403 "admin auth is not configured". That is the deliberate #95 replacement for "no password ⇒ everything open". Tests that used to rely on unauthenticated admin writes now set `admin_auth.ADMIN_PASSWORD` in their fixture.
- **Two hash primitives, on purpose**: 256-bit random secrets (agent tokens #94, session tokens) → `sha256` at rest (nothing to brute-force, O(1) lookup); human passwords → `hashlib.scrypt(n=2^14, r=8, p=1)` stored self-describing as `scrypt$n$r$p$salt$hash` so parameters can be raised without a migration. `_dummy_hash()` is verified for unknown names so response time does not enumerate principals.
- Sessions live in **SQLite** (`admin_sessions`), not process memory: uvicorn runs multiple workers, and an in-memory session works only with sticky load balancing. Checked on every use: `revoked_at`, absolute `expires_at` (TTL) and `last_seen_at` (idle). `last_seen_at` refresh is throttled to one write per session per minute (`TOUCH_INTERVAL_SECONDS`).
- Sessions opened with the legacy shared `ADMIN_PASSWORD` are stored with `principal_id="legacy"` and die with the password — clearing `ADMIN_PASSWORD` drops the server to read-only mode rather than leaving an admin session alive.
- Lockout state is **in memory** (`_FAILURES`, `_LOCKED_UNTIL`) and per worker: a brute-force attempt must not become one SQLite write per guess. `_prune_lockouts()` runs on *every* failure (not only when a lockout fires) so a spoofed-IP flood cannot grow the map; `MAX_LOCKOUT_ENTRIES` caps it.
- `X-Forwarded-For` is honoured **only** with `TRUST_PROXY_HEADERS=true` (`auth.client_ip`). Untrusted, it would give every client one shared lockout bucket (self-DoS) and put a fabricated IP in audit lines — the same reasoning that keeps #94's mTLS unenforced.
- Audit is now `server/audit.py::audit_event` (extracted from `agent_auth`, which re-exports it). It drops fields whose names look like credentials (`_FORBIDDEN_KEYS`) and never raises. #97 replaces the sink; call sites stay put.
- Alert secrets are redacted at the API edge (`server/alerts.py`): `redact_config()` masks `webhook_url` (as `scheme://host/***REDACTED***`) and `headers`; `merge_redacted()` treats the sentinel (exact **or** suffix) as "keep the stored value", so a UI round-trip cannot wipe a webhook. `PUT /alerts` and `GET /alerts` both pass through them.
- MCP exposes `auth_status` + `whoami` only: **no login, principal or session tools at all** — identity minting is a human/IaC action (epic #93 D9 extended to identity).
- New env vars (#95): `ADMIN_SESSION_TTL_SECONDS` 3600, `ADMIN_SESSION_IDLE_SECONDS` 900, `ADMIN_LOGIN_MAX_ATTEMPTS` 5, `ADMIN_LOGIN_BACKOFF_SECONDS` 30, `ADMIN_LOGIN_MAX_BACKOFF_SECONDS` 900, `TRUST_PROXY_HEADERS` false. - `_env_int` ignores non-positive/garbage values and warns, rather than letting `ADMIN_SESSION_TTL_SECONDS=0` silently mean "sessions never expire" or "always expired".

- Config push posture lives in `server/posture.py` (#96): every flag read at call time; `push_allowed()` = flag on AND posture met (or `OPAMP_ALLOW_INSECURE_CONFIG_PUSH=true`). `assert_startup_posture()` is called from `lifespan` and from `__main__`; uvicorn exits **3** on lifespan startup failure. - Agent auth (#94) lives in `server/agent_auth.py` + `SQLiteCredentialStore` (`agent_credentials` table in `server/state.py`, WAL). Credential = `Authorization: Bearer opamp_agent_…`, SHA-256 at rest, returned once by `POST /agents/{id}/token`; `agent_id` is the hex `instance_uid` and the token is bound to it at mint time. 401 (no/bad/revoked) before protobuf parsing, 403 (uid mismatch / binding conflict) before `_apply_status_report`; WS closes 1008 pre-`accept()`. - Upstream verification for credential headers: `extension/opampextension@v0.140.0` has `commonFields.Headers` (configopaque) under `server.http` **and** `server.ws`, passed via `types.StartSettings.Header`; opamp-go sets them on every HTTP request and on the WS dial. The supervisor has the same. **But the extension registers no `OnOpampConnectionSettings` callback**, so it cannot receive a server-issued credential in-band — bootstrap must be out-of-band (`agent_auth.collector_snippet()` / `opampctl agents token create`), and registration-on-first-use stays with #83.
- `ConnectionRegistry` is principal-aware now (`bind(conn_id, uid, principal)`, `principal_for(uid)`): same principal may move a binding (legit reconnect), a different principal is refused in `_handle_agent_message` before state is touched, and an authenticated principal pre-empts a leftover `None` (off-mode) binding. Cross-principal takeover is already impossible in token mode because token→uid is 1:1; the registry check is defence in depth for mTLS/other principals later.
- MCP write gate starts here: `OPAMP_MCP_ALLOW_WRITES=true` makes `create_agent_token`/`revoke_agent_token` *exist* (`mcp_server.server._register_write_tools()`); absent otherwise, per D9/#106. `mcp._tool_manager.remove_tool(name)` is how tests undo registration.
- `agent_auth` refreshes `last_seen_at` at most once per `TOUCH_INTERVAL_SECONDS` (60s) — authenticating runs on every agent poll, so an unthrottled UPDATE would be a SQLite commit per message.

- OpAMP write path (#109): `AgentRegistry.update(persist=False)` batches and returns whether anything actually changed; `AgentRegistry.persist(agent_id)` is the *only* place an agent row is written. `_apply_status_report()` collects all field groups into one dict → one in-memory apply → at most one upsert, so a no-op heartbeat writes nothing. `last_heartbeat` never counts as a change; `HEARTBEAT_PERSIST_SECONDS = 60` in `server/main.py` flushes a heartbeat-only row at most once a minute so a restart doesn't look like a stale fleet (or immediately reap everyone). Measured 452 → 1,728 msg/s (8 clients, p99 5.3 ms); `scripts/bench_opamp_capacity.py` has a warm-up pass (registration writes are not steady state) and `BENCH_CLIENTS` client processes because one client process is GIL-bound at ~1,200 msg/s.
- `synchronous=NORMAL` in WAL was measured for #109 and gave nothing (0.35→0.34 ms/upsert) — do not weaken durability for that. Connection reuse across store calls is still on the table (issue item 3, not done).

- **Redaction (#98)** is `server/redaction.py` and there is exactly one of it: `redact_document()` (replace values, keep shape, return paths — for display) and `scrub_fields()` (drop keys — for audit/logs). `AgentState.to_dict()` is the API choke point; the per-agent result is cached on the instance keyed by the raw string, because `GET /agents` walks every agent (#109).
- **Config bodies are strings, not mappings.** An OpAMP body is `bytes` and `MessageToDict` renders it **base64**, so key-name matching sees nothing: `_walk()` therefore also runs `scrub_text()` on every string and decodes plausible base64 bodies (`decode_text_body()`), scrubs, and re-encodes. Without that, `/agents` leaks every exporter password in the effective config. `contains_redaction()` checks the same base64 form, or a round-tripped GET response could be pushed back.
- **Regex performance is a security property here.** `scrub_text` runs on every log record and audit detail. An alternation of secret words inside the pattern (or an unbounded `[A-Za-z0-9_.-]*` / scheme class) is quadratic: a 20 KB log line took 28 s. Pattern finds `identifier: value` with bounded classes, predicate (`_SECRET_WORD_RE`) decides if the key is secret. `tests/test_redaction.py::test_scrubbing_is_linear_enough_for_a_log_line` is the guard.
- The loguru filter is a **patcher**, not a sink filter (`logger.configure(patcher=…)`), because the requirement is that no sink ever sees the secret — including sinks a library adds later, and including the formatted traceback, which a filter cannot rewrite (the patcher renders, scrubs, appends, and clears `record["exception"]`). Uninstall with `patcher=[]`; `patcher=None` means "leave it alone".
- `key_file` is a **path**, not a secret: do not redact it. Redacting paths hides debugging information and protects nothing.
- **Crypto (#98)** is `server/crypto.py`: AES-256-GCM, envelope `enc:<key_id>:<b64url(nonce||ct)>`, `key_id` = first 8 hex of SHA-256(key) so rotation needs no `key_version` column. AAD is namespaced (`opamp-config:agent:<id>` / `opamp-config:revision:<id>`), so a ciphertext copied between rows fails to decrypt. `CONFIG_AT_REST_KEY_PREVIOUS` is read-only; rotation = new key + previous + `opampctl config rotate-key --db`, then drop previous.
- Effective configs are sealed **inside the existing TEXT column** (no schema change, no unreadable window). A row that fails to decrypt keeps `sealed_effective_config` and is written back byte-identical — never NULL — so supplying the right key later still works. Per-row failure, not per-fleet: one undecryptable row must not 500 `GET /agents`.
- `config_at_rest` is the **fifth** config-push posture requirement (#98): met when a key is configured *or* `OPAMP_ALLOW_PLAINTEXT_CONFIG_STORAGE=true` (an explicit decision, reported as `plaintext` in `/health`). "Nobody set the key" (`unconfigured`) is a refusal.
- `secret:read` is implemented as `role_satisfies(principal.role, ROLE_APPROVER)` on `GET /agent/{id}/config?reveal=true`, audited as `config.reveal`, `Cache-Control: no-store`. MCP has **no** reveal parameter at all.
- **Effective config (#68)** is read in exactly one place, `server/effective_config.py` (`objects()` → `parse_effective_config()` union of component usage, `preferred_object()` for display; `ui/config_view.py` renders it, streamlit-free so it is testable). Config-map keys are agent-defined, so **every** object is parsed and components are **unioned** — never "the `""` object". Skipping rules: non-YAML `content_type`, non-UTF-8 body, unparseable body, non-mapping document — each skipped individually with a debug log, never raised. Parsing goes through `config_validation.parse_document()` (bounded loader, duplicate keys refused) because the document is agent-supplied. A role is a *preference hint* for display, not a filter.
- **`AgentConfigObject.role` is now pushable** (#66 made it expressible, #68 made it survive the pipeline): `check_shape` accepts and bounds it (`MAX_ROLE_CHARS=128`, because `CONFIG_MAX_BYTES` only counts bodies), `compute_hash` appends it **only when non-empty** (so pre-upgrade revisions keep their hash rather than being re-pushed fleet-wide; golden hash in `tests/test_remote_config.py`), and `build_config_map` sets it on the wire. Do not "simplify" the conditional out of the hash.
- **Remote config (#81)** is `server/remote_config.py` (domain) + `SQLiteDesiredConfigStore` (`server/state.py`): `config_revisions` is append-only (body sealed under AAD `revision:<id>`, `failed_at` poisons it) and `desired_configs` is the per-agent pointer + previous revision. `DesiredConfigRegistry` caches decoded current revisions in memory because the message path must not read SQLite (#109); it reloads at startup and on push.
- **Hash**: SHA-256 over a length-prefixed, key-sorted encoding of the config map. Spec §Calculating Hashes makes the hash server-defined ("the Agent never calculates hashes, it only stores and compares them"), verified against `cmd/opampsupervisor` — it persists the received `AgentRemoteConfig` and echoes `GetConfigHash()` back. Length prefixes matter: without them `{"ab":"c"}` and `{"a":"bc"}` collide.
- **`RemoteConfigStatus.status` from `MessageToDict` is the full enum name** (`RemoteConfigStatuses_APPLIED`) in this proto, which is what `AgentState.remote_config_status` has always stored. Comparisons must go through `remote_config.short_status()`, or a `FAILED` never matches and the server re-pushes forever (T9).
- Delivery rule (`offer_for`): push allowed → agent advertises `AcceptsRemoteConfig` → revision exists → not poisoned → reported hash differs. **Withdrawal is not a special case**: it is an empty config map revision, which is the spec's own "run your local config".
- Only a `FAILED` whose `lastRemoteConfigHash` is **ours** poisons a revision; a failure the agent reports for something else is not ours to punish. Poisoning is permanent for that revision id — retrying means pushing a new revision (D6).
- `PUT /agent/{id}/config` requires **`approver`**, not `operator`: until #99/#103 land the two-phase flow, a direct push *is* the approval. Fleet apply needs `admin` + `"confirm": true` + an explicit selector (a missing selector is a 400, never "all agents").
- Proto is now **opamp-spec v0.20.0** (#66): package `opamp.proto.v1`, `AgentConfigObject` (`body`/`content_type`/`role`), `ComponentHealth.attributes` (field 7). Flat layout is kept, so the one intentional deviation from upstream is `import "proto/anyvalue.proto"` (not `opamp/v1/...`) — that is what makes the stubs import each other as `from proto import anyvalue_pb2` and every call site keep using `proto.opamp_pb2`. Regenerate with `./scripts/generate_proto.sh` (pins protoc 34.1 = the `protobuf>=7.34.1` floor; the stub's `ValidateProtobufRuntimeVersion` is what makes the floor real). `tests/test_proto_sync.py` pins the package, every pre-existing field number, a golden pre-v0.20.0 wire payload, and the two new fields — a renumbering is otherwise invisible to review.
- The proto can express `role` but the **push pipeline cannot carry it yet** (canonical hash, `build_config_map`, wire round-trip and the API all see body+content_type only), so `validate_config_map()` still rejects `role` — now pointing at #68 (wire it end-to-end) instead of #66. Accepting it would approve one object and deliver another.
- New env vars (#98/#81): `CONFIG_AT_REST_KEY`, `CONFIG_AT_REST_KEY_PREVIOUS`, `OPAMP_ALLOW_PLAINTEXT_CONFIG_STORAGE`, `CONFIG_MAX_BYTES` (1 MiB), `CONFIG_RETENTION_DAYS` (30, superseded bodies only — the current revision is never pruned). `cryptography>=42` is now a real dependency.
- `tests/test_audit.py::AUDITED_ROUTES` gained `config.push` / `config.withdraw` / `config.apply`; `/config/validate` is in `EXPLAINED_ROUTES` (pure function).

- **Config control plane (#99)** is `server/config_control.py` (lifecycle, no SQL, no FastAPI) over `SQLiteDesiredConfigStore`. Statuses `proposed → active → superseded | rolled_back | poisoned`, plus `rejected`; only `active`, unpoisoned, not-`unconfirmed` revisions are deliverable (`remote_config.deliverable()`). A **proposal** is one `proposal_id` across N per-agent revisions — that is how a selector/fleet scope stays one operator action while revisions stay per-agent and immutable. The issue's `config_assignments` table is `desired_configs` **plus** the delivery columns (`delivered_hash`, `delivered_at`, `last_status`, `attempts`, `poisoned`, `unconfirmed`): two tables for "what should it run" and "did it get it" would disagree. `config_rollouts` was deliberately not created — that is #101.
- **Selector scope resolves at approve time**, not propose: `approve()` re-resolves the filter, creates revisions for newly-matched agents, skips (`dropped`) agents that stopped matching, and stores `scope_json.resolved_agents`. `include_future` is honoured only by `reconcile_future()` from the periodic tick (never the message path), and "already attached" is read from the proposal's own revision rows, not from `scope_json` — the immutable scope_json cannot be updated, so the rows must be the truth.
- **Auto-revert (T9) is a delivery-tracking problem, not a status problem.** The supervisor restores `last_working_remote_config.dat` and reports the *old* hash, so a plain hash comparison loops forever. `note_status()` poisons when: `FAILED` with our hash; or a reported *known older revision* while `delivered_hash == ours` and (`status == FAILED`, or the grace window `CONFIG_REVERT_GRACE_SECONDS` has passed **and** `attempts >= 2`). The grace+attempts gate exists because a lagging report during a supervisor restart looks identical to a revert — poisoning a healthy rollout is its own incident. The history lookup (`hashes_for_agent`) only runs inside that branch: it is a SQLite read and `note_status` is on every message (#109).
- Delivery is bounded per assignment (`CONFIG_MAX_DELIVERY_ATTEMPTS`, default 5) → `unconfirmed=1` + a log line, never an infinite re-push. `delivered_hash` is persisted so a restart cannot double-deliver.
- **One active revision per agent is enforced in the store** (`_assign_on()` supersedes the old row inside the same transaction), so direct push / withdraw / fleet apply / approve cannot diverge; poisoned and rolled-back rows keep their status (`WHERE status='active'`).
- Drift = "is the agent running what we approved". Not a hash compare (the supervisor composes and re-serialises, so a byte compare reports drift on every healthy agent): `config_validation.document_drift()` checks the desired document is *contained* in a reported effective body (subset for maps, subset for lists, equality for scalars). `drift` is `true | false | null` (`null` = not active / not connected / no effective config). Computed on demand **and** swept in the periodic tick, memoised on `(revision_id, desired hash, reported hash, hash(effective_config))`. One `config_drift` alert per (agent, revision) — `_DRIFT_ALERTED` re-arms when the drift clears.
- Audit actions (#97 inventory updated): `config.propose`, `config.approve`, `config.reject`, `config.reactivate`, `config.rollback`, `config.override` (policy override; requires a recorded reason), plus system-emitted `config.apply.failed` (with `reason: failed|auto_reverted`), `config.drift`, `config.apply.future`.
- **Validation (#100)** is `server/config_validation.py` — pure functions, no FastAPI/SQLite (same rule as `manifest.py`/`reports.py`). Order: shape+size → bounded parse → structure → protected invariants → inventory → OPA → verdict. `remote_config.validate_config_map()` is now a thin compat wrapper that raises `ConfigValidationError`; `check_config_map()` returns the `Verdict`.
- **Severity policy (do not "simplify" this):** a body with **no** collector sections is not judged (a PEM, a routing table); a body with collector sections but **no `service`** is a *fragment* and only warns; a body **with `service`** gets structural rules and D7 invariants as **errors**. Without that split every partial config object in a multi-object map becomes unpushable.
- Parse guards are inside a `SafeLoader` subclass, not a pre-scan: alias budget (`AliasEvent` count), depth budget (`compose_node`), **duplicate keys are an error** (PyYAML is silently last-wins; a `<<` merge key disables the check for that mapping because merge+override is legal), and an **expanded-node budget** (`check_expansion`, explicit stack). PyYAML shares anchored nodes so it does not blow up at parse time — the explosion happens on later expansion (JSON dump, drift compare), which is exactly what the node count measures. Test asserts a wall-clock ceiling.
- **Protected invariants (D7)**: `extensions.opamp` present **and** `opamp` in `service.extensions` → error (dropping it orphans the agent with no remote fix); the `opamp` endpoint must resolve to this server (`posture.public_url()`, `OPAMP_SERVER_ENDPOINT`/`OPAMP_WS_ENDPOINT`/`OPAMP_HTTP_ENDPOINT`, `CONFIG_ALLOWED_OPAMP_ENDPOINTS`) — matching is **host-based**, because moving the channel to another machine is the outage and a path/scheme tweak is not. `allow_endpoint_change` downgrades it to a warning, and the approver must confirm again at approve time.
- Warnings never block: no `memory_limiter`, no `batch`, no `service.telemetry`, exporter host off `CONFIG_ALLOWED_EXPORTER_HOSTS`, and a component missing from the target agent's `available_components` (aggregated per component across agents — one warning naming a few agent ids, not one per agent).
- The **policy gate** has three distinguishable outcomes and they must stay distinguishable: `skipped` (OPA disabled — never reported as a pass), `violations` (blocks; approver `override_reason` proceeds, audited), `error` (fails closed). `verdict.fingerprint()` covers errors+warnings+policy so a re-validate can tell "changed" from "same".
- Validation runs at **propose** (blocking errors refuse; policy violations are stored so an approver can override — refusing there would make the override unreachable for a non-approver) and again at **approve** (`409 re-validate: …` on blocking changes; warning-only changes are reported and proceed).
- `verdict_json` is stored on the revision, and `revision_view()` never includes a config body — listings are metadata only (D8), with `GET /agent/{id}/config` remaining the only (redacted) body surface.
- New env vars (#99/#100): `CONFIG_MAX_ALIASES` 10000, `CONFIG_MAX_DEPTH` 50, `CONFIG_MAX_NODES` 100000, `CONFIG_ALLOWED_EXPORTER_HOSTS`, `CONFIG_ALLOWED_OPAMP_ENDPOINTS`, `CONFIG_MAX_DELIVERY_ATTEMPTS` 5, `CONFIG_REVERT_GRACE_SECONDS` 120. `/config/posture` reports them under `remote_config`.
- Layer parity (#99/#100): `opamp_client.propose_config/list_config_revisions/get_config_proposal/approve_config/reject_config/reactivate_config/rollback_agent_config`; `opampctl config propose|revisions|show|approve|reject|reactivate` + `agents config rollback` (revisions/show also work offline via `--db`); MCP `list_config_revisions` always, `propose_config` **only** with `OPAMP_MCP_ALLOW_WRITES=true`, and approve/reject/reactivate/rollback/apply are never MCP tools at any setting.
- `tests/test_config_control.py` is the #99 acceptance-criteria file (propose delivers nothing, supersede+rollback, auto-revert over 5 polls, stale cleanup keeps the assignment, a new uid inherits nothing, selector-at-approve + include_future, one drift alert, restart without double-delivery, old-DB migration). `tests/test_config_validation.py` + `tests/fixtures/configs/` is the #100 corpus, one fixture per stage.
- **Stale-agent expiry (#69)** is cadence-based: `max(AGENT_TIMEOUT_SECONDS=180 floor, 3 × EWMA of the agent's own inter-message gaps)`, with `AGENT_FIRST_CONTACT_SECONDS=900` while the cadence is untrusted. Learning lives in `AgentState.record_report()` (`MIN_REPORT_GAP_SECONDS=1.0`, α=0.3, needs 2 informative gaps because a restart measures its first gap from a *persisted* heartbeat). `AGENT_REGISTRY.update()` deliberately **no longer** moves `last_heartbeat`: it is a server-side mutation, and a compliance check used to keep a dead agent looking alive forever. Only `record_report()` (called once per message from `_apply_status_report`) counts as liveness. `cleanup_stale_agents(now=...)` takes an injectable clock; `GET /agent/{id}` exposes `report_interval_seconds` + `stale_timeout_seconds`, and the removal log line carries silence/timeout/interval.

## Three live bugs found by probing the code (all in chunk 1)

**Status: all three fixed in the next section (chunk 1 landed).**

- **Capabilities are over-claimed.** `remote_config.server_capabilities()` returns `117` = `AcceptsStatus|AcceptsEffectiveConfig|AcceptsPackagesStatus|OffersConnectionSettings|AcceptsConnectionSettingsRequest`. The last two have **no implementation** (#83), so a supervisor is entitled to wait for a connection-settings offer that never arrives. `AcceptsPackagesStatus` is honest — `package_statuses` really is persisted (`main.py:902`, `state.py:73`). Plan: classify every enum value in `SUPPORTED`/`NOT_SUPPORTED` and let a test fail when a proto bump adds an unclassified capability — that guard is the durable fix, dropping two bits is the symptom.
- **An empty `instance_uid` is accepted.** Verified: `_handle_agent_message(b'')`-style message with no uid registers under agent id `''`, so every uid-less agent shares one row and they overwrite each other. Malformed protobuf likewise answers `200` + capabilities instead of `400`. `RequestInstanceUid` (a **flag bit** `AgentToServerFlags_RequestInstanceUid = 0x1` on `AgentToServer.flags`, not a field) is unhandled. Plan: 400/WS-1002 for empty uid and parse failures; mint a uuid4 in `off` mode; **refuse in token mode** (a minted uid has no credential — D1). Non-16-byte uids stay accepted (every test/harness/bench client uses readable ascii uids), recorded so nobody "fixes" it.
- **HTTP has no message size limit while WS does.** WS enforces `OPAMP_MAX_MESSAGE_BYTES` (64 MiB) and closes `1009`; `opamp_endpoint` does `await request.body()` with no cap, so one POST OOMs the process. #72 fixes it by reusing `framing.max_message_bytes()` (which #89 deliberately left there), rejecting on `Content-Length` first and then bounding the streaming read (the chunked/lying-header case is the one that actually blows up). Note for #71: the limit applies **post-decompression**, so gzip must be unrolled inside the bounded stream, not before it.

## Chunk 1 landed (#74, #73, #72) — 2026-11-02

- **#74 capabilities.** `server/remote_config.py` now classifies every proto bit in four disjoint buckets — `ALWAYS_ADVERTISED_CAPABILITIES` (`AcceptsStatus`, `AcceptsEffectiveConfig`, `AcceptsPackagesStatus`), `CONDITIONAL_CAPABILITIES` (`OffersRemoteConfig`, only while `posture.push_allowed()`), `UNIMPLEMENTED_CAPABILITIES` (each mapped to `#82`/`#83`) and `RESERVED_CAPABILITIES` (the zero sentinel) — with `CLASSIFIED_CAPABILITIES` as their union. `server_capabilities()` returns **`0x15` (21)** normally and **`0x17` (23)** with push allowed. `tests/test_capabilities.py` pins the exact value and fails when a proto bump adds an unclassified bit; `test_push_delivery` now compares the push frame to `server_capabilities()` instead of duplicating the mask. README gained a "Server capabilities" section.
- **#73 BAD_REQUEST + uid.** New `server/protocol.py` owns `BadRequest`, `error_response()` (a spec-shaped `ServerToAgent.error_response{BadRequest}` with `instance_uid` echoed) and a 15-line `uuid7()`. HTTP answers **400** with that protobuf body (so non-OpAMP callers still see a failure); WS sends the same error frame then closes **1002**. Empty uid and parse failures are refused before any registry/SQLite write. `RequestInstanceUid` mints a UUIDv7 in `off` mode, applies the message under the minted id, removes a stale temporary record, and keeps the reply addressed to the temporary uid; with `OPAMP_AGENT_AUTH=token` it is refused (D1: a minted uid has no credential). **Deliberate deviation from #73's checklist:** non-16-byte but non-empty uids stay accepted (the "19-byte uid → BAD_REQUEST" box is not ticked) — every harness/bench/existing fleet uses readable ASCII ids and the uid is not a security boundary; the reasoning is a comment in `protocol.py` and no fixture churn was needed.
- **#72 HTTP size limit.** New `server/http_body.py:read_body()` caps `Content-Length`, the streamed bytes, and the **decompressed** gzip bytes, in that order; 413 is raised before `_handle_agent_message`, so nothing registers or bumps metrics. Gzip request bodies are now decompressed here (that is #71 items 1–3; #71 still owns `GZipMiddleware` response compression and the parity tests). Corrupt gzip and unknown `Content-Encoding` are 400 BAD_REQUEST. Oversized responses are logged and replaced with an empty ack. `/v1/metrics` is intentionally outside the OpAMP limit and documented as such in README + `.env.sample`.
