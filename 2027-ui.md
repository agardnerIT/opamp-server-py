# 2027 UI — polish, fixes, and the design pass

Companion to `new-ui-plans.md`. Stages 1–9 of that plan are **done**: every
Streamlit page has a working counterpart in `web/`. This plan is what comes
next — the "Bugfixes and Changes 1" list from the owner (reproduced at the
bottom, annotated) plus a full visual/interaction pass so the console stops
looking like a stage 1 scaffold and starts looking like it was designed on
purpose.

Same rules as `new-ui-plans.md` apply, unchanged: `cd web && npm run build &&
npm run test` (and `npm run e2e` when touched) green before a session ends;
tokens only in `src/index.css`; all HTTP via `src/api/`; 401 vs 403 sacred;
`<redacted>` is opaque; role gating is a client-side hint only; screenshots
into `docs/screenshots/console-*.png` for meaningful screen changes; do not
touch `ui/` until cut-over (stage 10 there).

Status vocabulary: **todo / in-progress / done**. Each stage is written to be
picked up by an independent agent session: read this header, your stage, and
any stage marked `depends on` that is **done**. Root causes found during
planning are recorded inside each stage — trust them, they were verified
against the code on 2027-01.

## Ground rules specific to this pass

- **Design reference, not pixel targets.** The visual direction is described
  in Stage A; when implementing a stage, load the named skills
  (`frontend-design`, `better-interface`, `better-typography`, `better-colors`,
  `better-layout`, `better-motion`) and follow them.
- **Existing primitives win.** Stage 5 built `StatusBadge`, `Section`,
  `KeyValue`, `EmptyState`, `SqlSearch`, `AgentTypeBadge`, `Modal`; stage 6
  built `ComposeStepper`, `RolloutMonitor`, `Diff`. Restyle them in place —
  do not fork them per page.
- **The mock is the dev rig.** `VITE_USE_MOCK_API=1 npm run dev` (see
  `web/README.md`). Mock is auth-stateful and principals-mode (login as
  `viewer`/`operator`/`approver`/`admin`, shared password in
  `fixtures.mockPrincipals`). E2E must navigate by sidebar links after mock
  login, not `page.goto` (a reload resets the JS session flag — though the
  localStorage mirror in `mock.ts` now survives plain `goto`s, keep the
  sidebar-link habit anyway).
- **Port 8501 is the product port** (Streamlit's old one). Stage B moves the
  dev server and compose stack to it.

Owner direction (2027-01): **not a hacker aesthetic — accessible modern
SaaS**. Think Linear/Vercel polish on the brand's indigo-on-near-black
dark scheme: soft low-alpha borders, clean hierarchy, generous touch
targets, mono only where data is genuinely monospaced (SQL, config,
IDs), never as a stylistic blanket.

Design decisions locked at A1 (per `frontend-design` calibration pass):
- **Type**: Inter Tight (variable, self-hosted) for display/metrics (the
  plan's Geist/Inter-Tight-class pick — modern-SaaS, not techy-quirky);
  Inter (variable) for body; JetBrains Mono (variable) for
  SQL/config/IDs only. Scale 12/13/14/16/20/28.
- **Color roles**: accent #5488e8 = interactive text/links/borders only;
  #4051b5 = solid primary fills (buttons); #02a6f2 = focus ring, active
  nav marker, hero gradient. Semantic ok/warn/danger/info exist ONLY as
  tones through `statusTone`. No hex in components.
- **Shape/depth**: radius 6/10/14; hairline low-alpha indigo borders +
  inner top highlight instead of drop shadows.
- **Motion**: 140ms out / 200ms in, `cubic-bezier(0.2,0,0,1)`;
  `prefers-reduced-motion` kills transitions/animation.
- **Copy**: sentence-case micro-labels, no tracked-out caps eyebrows, no
  middle-dot join decoration.

Depends on: nothing. **Do this before any new screens** — every later stage
assumes its primitives exist.

Goal: replace the "default Tailwind on a dark background" look with an
opinionated 2027 console aesthetic. Direction:

- **Feel**: precision instrument, not dashboard template. Dense where data is
  dense (tables, logs, diffs), airy where the user is deciding (steppers,
  empty states, onboarding).
- **Type**: one distinctive display/heading face for titles and metrics
  (self-host, subsetted — e.g. Geist/Inter-Tight-class), system stack for
  body, one good mono for config/SQL/hash (JetBrains Mono class). Establish a
  real scale (12/13/14/16/20/28) instead of ad-hoc `text-sm` everywhere.
- **Color — on brand (owner decision, 2027-01)**: black/near-black surfaces
  plus the brand blue from agardner.net. The site is MkDocs Material: primary
  **indigo `#4051b5`** (default scheme, what renders first), link blue
  `#5488e8`, and its dark scheme swaps primary to **light-blue `#02a6f2`**
  (verified against the site's palette CSS, 2027-01). Derive the token set
  from that family:
  - `--color-accent: #5488e8` as the everyday interactive blue on dark
    surfaces (it is the exact link blue the brand site pairs with its
    indigo primary); `#02a6f2` reserved for high-emphasis moments (active
    nav, focus rings, hero) or a `#4051b5 → #02a6f2` gradient for the
    wordmark/hero.
  - Backgrounds: neutral near-black with the site's own faint indigo cast
    (its dark scheme is `hsl(230°, 15%, 14%)`) — e.g. bg `#14161c`, surface
    `#1b1e27`, surface-2 `#232735`, borders as low-alpha indigo-grey.
  - Keep a fixed semantic set (ok/warn/danger/info) mapped through
    `statusTone` only, tuned to harmonize with indigo (the site's own
    deep-orange accent family can inform the warning tone). Verify contrast
    with the `better-colors` skill. No hex in components, ever.
- **Depth & shape**: subtle elevation via border + inner highlight rather
  than drop shadows; consistent radius scale (`--radius-*`: 6/10/14);
  hairline `1px` borders with low-alpha tokens.
- **Motion**: `better-motion` skill. One duration/easing pair
  (fast ≈120–160ms out, enter ≈200ms); use for: nav active-state, panel
  enters, stepper transitions, StatusBadge state changes. Respect
  `prefers-reduced-motion`.
- **Primitives to build once, in `src/components/ui/`** (thin, token-based,
  unit-testable where logic exists):
  - `Switch` (replace all tiny checkboxes; ≥28px hit target — the owner
    explicitly called the native checkboxes tiny),
  - `Checkbox` (only where multi-select semantics are real),
  - `Tooltip`/`InfoHint` (the (i) affordance Stage D/E/F need — wrap native
    `<dialog>` or title-based fallback; keep it dependency-free),
  - `Toast`/`inline notice` component (replace per-page `message` state
    strings),
  - `Tabs` (used by Alerts selector today, needed by AgentDetail),
  - `Button` variants (primary/secondary/ghost/danger) — one place, stops
    five invented styles (the original shadcn rationale, satisfied without
    the dependency tree),
  - `PageHeader` (title + one-line lede + actions slot) — every page uses it.
- **Restyle pass over all existing components/pages** using the above. No
  behavior changes in this stage except where a primitive replaces markup
  (checkboxes → Switch).
- Update `docs/screenshots/console-*.png` set via the five
  `web/tools/screenshot-*.mjs` scripts; refresh the README "Latest screens"
  table.

Done when: tokens + primitives exist, every route renders through them,
`npm run build && npm run test && npm run e2e` green, screenshots refreshed.

## Stage C — Bugfix batch 1 (status: **todo**)

Depends on: Stage A (primitives it consumes). Can be split into two sessions:
C1 = SQL + RemoteConfig, C2 = Alerts + Sessions + Compliance + Updates.

Root causes were verified against the code during planning. Do not
"re-investigate" these — fix them.

1. **SQL suggestions ignore SQL keywords** (`src/lib/sqlSuggestions.ts` +
   `src/components/SqlSearch.tsx`). Owner: typing `S` offers `capabilities`
   instead of `SELECT`. Cause: the helper only completes *column* names, by
   substring, and `capabilities` contains `s`. Fix:
   - Add a keyword tier (`SELECT`, `WHERE`, `ORDER BY`, `LIMIT`, `LIKE`,
     `AND`, `OR`, `ASC`, `DESC`, `COUNT(*)`…) with the fleet's SQL dialect
     (see `docs/sql-agent-queries.md`); keywords match by **prefix**.
   - Rank: keyword prefix > column prefix > column substring. A bare `S`
     must offer `SELECT` first.
   - `sqlSuggestions` is pure + unit-tested — extend `sqlSuggestions.test.ts`
     (typo'd tests expect quoted `dep` inserts; don't break the
     `"host.arch"` quoting contract).
2. **RemoteConfig "saved group" crash** — `ComposeStepper.tsx`: `ReferenceError:
   Cannot access 'selectedGroup' before initialization`. Cause: `targetIds()`
   reads `selectedGroup`, but `targetIds()` is *called during render* at
   `const diffAgentId = … targetIds().length …` which executes **before**
   `const selectedGroup = …` is initialized (TDZ). Fix: hoist
   `selectedGroup` above `diffAgentId`, or make `targetIds` take the group
   explicitly. Add a regression e2e: Remote Config → choose target mode
   "saved group" → must not error (currently reproduces via the mock).
3. **Alerts "Enabled" checkbox dead on first event** (`src/routes/Alerts.tsx`).
   Cause: `event` state starts `null`; `effectiveEvent = event ?? events[0]`,
   but `draftFor` only returns the draft `if (draft && event === name)` —
   with `event === null` the freshly-toggled draft is discarded on the next
   render and the server config re-renders. Toggling to another event sets
   `event`, which is why it then works. Fix: seed `event` with `events[0]`
   once data loads (or key the draft by its own event name instead of the
   selector state). Also: swap the checkbox for the Stage A `Switch`, and
   give each event its one-sentence lede ("Receive an alert when a new agent
   connects to this server", etc. — a static `EVENT_DESCRIPTIONS` map is
   fine; keep event names server-canonical).
4. **Alert headers client-side validation** (stage-11 backlog #2 there):
   JSON-parse before save; surface a field-level error instead of a 422 from
   the server. Fold into the C2 session since Alerts is open anyway.
5. **Alert secret UX** (backlog #1): masked webhook/headers fields with a
   "replace secret" affordance that passes the `***REDACTED***` sentinel
   through untouched when the field is not edited. Contract unchanged.
6. **Sessions page hygiene** (`src/routes/Sessions.tsx`, server
   `server/auth.py`): expired sessions currently render forever. Check
   whether the server prunes them (grep `_is_expired` / session store
   writes); if not, add a UI-only filter toggle "Hide expired" (default on)
   + a bulk "clear expired" action if the API supports it; if it needs a
   server endpoint, it is sanctioned — follow the four-layer sync rule
   (endpoint → `opamp_client` → `opampctl` → MCP + tests). Owner also
   questions the page's value for a single-user app: keep the page (it is
   the only place to revoke a stolen session) but consider collapsing
   expired rows behind the toggle entirely.
7. **Remove "Extend session"** (owner: unnecessary for a one-person app):
   - Frontend: delete `ExtendForm` + `useExtendSession` usage from
     `SessionStatus.tsx`; remove `extendSession` from `src/api/session.ts`
     and its tests. Session-status slot keeps identity/role/expiry + Logout.
   - Server: `POST /auth/session/extend` (audited re-auth path) stays — it
     is API surface used by the client layer and tested. Do not rip server
     code in this stage; just stop the UI from offering it. Note the
     decision here when done.
8. **Compliance OPA dead-end** (`src/routes/Compliance.tsx`): the "OPA is
   not enabled" empty state must explain *how* to enable it — read
   `server/opa_client.py` + `docs/` for the env/connection details (OPA URL
   env var, policy format) and render an `InfoHint` panel with the exact
   startup steps and a pointer to the docs page for writing policies.
9. **Remote Config posture banner demotion** (owner: too prominent, possibly
   wrong): the wall-of-text warning becomes a compact "Read-only mode" chip
   in the page header with an `InfoHint` modal carrying the full unmet-
   requirements detail. **Verify against the server first**
   (`server/posture.py`, `GET` endpoint that returns posture state — find
   it in `docs/api-reference.md`): if the running config actually *is*
   pushable (owner believes it is), the banner text itself is a server
   truth-telling bug — report the discrepancy in the stage notes and fix
   server-side only if there is a real logic error; posture gating
   semantics are the server's authority.
10. **Release emails confusion** (`src/routes/Updates.tsx`): the section
    says the address is "not managed from here" with no action. Since the
    signup service is external and the API does not expose a subscribe URL
    (this is stage-11 backlog #4 in `new-ui-plans.md`), pick the honest
    minimum: collapse the section to a single `InfoHint` line with a real
    link to the signup form (hard-coding the project's signup URL is
    acceptable if the owner confirms it — otherwise link GitHub releases
    only). If the owner wants a real signup box later, that is a server
    API change first (`GET /updates` exposing `subscribe_url`) — do not
    iframe.

Done when: every numbered item above is either fixed with tests/e2e where
the harness allows, or explicitly recorded as owner-decision-needed in the
stage notes. All gates green.

## Stage F — BYO-agent console (status: **todo**)

Depends on: Stage A primitives; coordinate with the owner before starting
(the plan header's open-questions rule). The owner's ask: users with their
own OpenAI-compatible endpoint + token (OpenAI, OpenRouter, Claude-Code-
style gateways, opencode, ollama…) should be able to drive this app through
chat. We never ship an LLM — the user brings theirs.

Design:

1. **Settings surface** (Admin section, admin-only — it stores a bearer
   token): base URL, API key, model id, optional headers. Stored via a new
   server endpoint pair (sanctioned server change, follow the four-layer
   sync rule): store the key through `server/crypto.py` AES-GCM like every
   other secret, redact on read (`***REDACTED***` sentinel round-trip, same
   contract as alerts webhooks). If the owner prefers no server storage,
   fall back to per-browser `localStorage` + direct browser→provider calls
   and skip the server change — **ask before building**; the default
   recommendation is server-stored so the chat works across devices.
2. **Chat page** (`/console` or Admin → "AI console"): message list,
   composer, tool-call transcript rendering (collapsible per tool call),
   streaming if the endpoint supports it (SSE; degrade gracefully).
3. **Tools = the REST API.** Build the tool list *from* the generated
   OpenAPI schema (`src/api/schema.d.ts` / a build-time extraction from
   `openapi.json`) — every safe GET is a tool; mutations restricted to a
   curated allowlist (propose/approve/rollout/alerts/agent-tokens…) with
   the same role floors the server enforces, surfaced as read-only hints to
   the model via tool descriptions ("requires approver").
   - The chat executes tools through `src/api/` wrappers (never raw fetch)
     so 401/403/429/503 handling, redaction, and the global 401 redirect
     all apply. The model never sees credential values; `<redacted>`
     bodies are passed as opaque (the model must be told the sentinel
     means "keep stored value").
   - System prompt: short, factual, links the SQL guide for agent queries.
4. **Safety**: every mutating tool call requires a confirm chip in the UI
   before execution (the model proposes, the human clicks). Destructive
   endpoints (delete group, revoke token/session, rollback) always confirm.

This stage is deliberately last-but-one because it is the largest and most
novel. Done when: with a real endpoint configured, a round trip like "how
many agents are unhealthy?" and "propose a config to group X" works, e2e
covers the settings flow + a mocked chat turn (mock the *provider*
endpoint, not our API), and the owner has signed off on the storage choice.
